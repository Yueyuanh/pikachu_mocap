把蒙皮连续变形搬进实时预览

MeshCat 能不能给 Pikachu 角色“套皮”？结论：它的几何层做不了顶点蒙皮，但工程上有一条现成的 three.js/glTF 替代路径——而且仓库里还留着当年验证过的控制器。

结论：可行，且有现成骨架可复用

想做“顶点随多根骨骼加权、平滑变形的连续蒙皮”，必须离开 MeshCat，改用 three.js + skinned glTF。全链路工具已就绪（QWebEngine 6.6、Blender MCP、CDN 可达），历史 viewer.html 提供验证过的驱动接口。唯一未定的关键未知量是 FBX 骨名与 URDF 21 关节名的对齐程度。

能力边界

ROOT CAUSE

为什么绕不开 three.js：这是能力层的限制，不是实现细节。

MeshCat 不支持蒙皮

meshcat.geometry 里没有 SkinnedMesh 或骨骼蒙皮类（已实测）。只能放静态网格 + 逐关节刚体 set_transform——表现为“每根骨一个硬块”，关节处无变形。

three.js / glTF 原生支持

GLTFLoader 加载带蒙皮的 .glb → 拿到 SkinnedMesh.skeleton.bones → 设 bone.rotation 即实时蒙皮变形（CPU skinning）。这正是“连续套皮”所需的。

现成资产盘点

ASSETS

决定成本的第一是“有没有已做过的部分”。关键发现在这里。

资产状态对实现的意义
assets/glTF/viewer.html 可复用(历史) 一套完整 three.js 蒙皮查看器：加载 pikachu_role.glb → 遍历 SkinnedMesh → 逐骨 bone.rotation[axis]，带 WebSocket 外驱接口。
assets/FBX/ 4 个 fbx 现存 pikachu_skin_Tpose.fbx(2.4M)、pikachu_skin_self_rig.fbx(1.4M) 大概率是带蒙皮的精致皮肤——是“皮”的源头。
urdf/…/pikachu_v025.fbx 现存 原始角色 FBX（5.9M），备用皮肤源。
/glTF/pikachu_role.glb 已删除 历史 viewer 依赖它，现需从皮肤 FBX 重新生成。
离线 three.js / 本地 .js 缺失 需下载一次 three ESM 到本地（CDN 已验证可达）。

工具链就绪度

TOOLING

四个前提逐项核验过，全部成立。

QWebEngine 6.6（Qt 内嵌预览） Blender 经 MCP 运行（FBX→glTF 转换器） three.js CDN 可达（1.27MB） websockets 12.0 已装（WS 驱动通道）

驱动通道二选一：QtWebChannel（Python→页面直调 JS，免开端口，适合嵌入）或历史 viewer 的 WebSocket :8765 协议（{joint,axis,angle(弧度)}，适合独立浏览器打开）。

唯一关键未知量

UNKNOWN

整条链路里只有一个点需要“跑一次 Blender 导入/导出”才能定死：

FBX 骨名 vs URDF 21 关节名

若 skin 骨名 ≈ URDF 关节名（如 left_knee_joint）→ 零映射，URDF 角直接喂骨；若为 Blender 风格（DEF_…）→ 需一张映射表（复用 retarget_map 思路）。

rest-pose / 轴 / sign / bias

需核对骨骼 bind pose 与 URDF 基准是否一致，决定要不要补 sign 与 bias。这是整个方案最花时间、通常要迭代 1–2 轮的环节。

出于“本次先不改动”，此处在报告中标记为待实测，未做导入/导出。
